## Where things live today

- The Lua environment for filters is assembled in one place,
  `create_filter_environment_with` (`crates/pampa/src/lua/filter.rs`),
  from `(runtime, target_format, script_path, attribution, &LuaOptions)`.
  Native uses `Lua::new()` (full stdlib, so `os.exit` is libc `exit`);
  WASM uses a restricted stdlib plus synthetic `os`/`io`/`dofile`
  (`os_wasm.rs`, `io_wasm.rs`). The shortcode environment
  (`LuaShortcodeEngine::new_with`, `shortcode.rs`) builds the same
  namespaces from the same `LuaOptions`.
- `LuaOptions` (`crates/pampa/src/lua_options.rs`) is the host → pampa
  options bag: `dialects`, `module_roots`, `typst`. quarto-core builds it
  in `crate::lmd::lua_options(&project, runtime)` from three call sites:
  `UserFiltersStage` (`stage/stages/user_filters.rs:239`),
  `ShortcodeResolveTransform` (`transforms/shortcode_resolve.rs:1231`),
  and `lmd_execute.rs:752`. The first two have the document in hand
  (`ctx.document: DocumentInfo` with `input` absolute, `ctx.output_path()`;
  `RenderContext.document` for shortcodes).
- `quarto.version` is set by `register_quarto_version`
  (`quarto_api.rs:220`) to the literal `{0,1,0}`. pampa is version `0.0.0`,
  but it depends on `quarto-util` (workspace version, 0.36.0), whose
  `quarto_util::cli_version()` is already the one source of truth for the
  version string, including the nightly `QUARTO_VERSION_OVERRIDE`
  (bd-p4ljdp2e). `PANDOC_VERSION`/`PANDOC_API_VERSION` are plain tables
  set in `create_filter_environment_with`.
- `quarto.doc` is `register_quarto_doc` (`quarto_doc.rs:187`); it has no
  path fields.
- Active profiles: `ctx.project.config.active_config_profiles:
  Vec<ActiveProfile>`; `quarto_profile_env_value(&active) -> Option<String>`
  is the comma-joined value already handed to the `env` shortcode and to
  subprocess spawns (the documented "one deliberate exception" to
  real-environment-wins). Profiles resolve for single-file renders too
  (`project/mod.rs:2172`).
- Quarto 1 reference: `external-sources/quarto-cli/src/resources/pandoc/datadir/init.lua`
  lines 595–715 (`projectDirectory`, `inputFile`, `outputFile`,
  `version`), 985–994 (the `quarto.doc.{input,output}_file` and
  `quarto.project` table). `project-offset` comes from
  `projectOffset()` in `src/project/project-shared.ts:131`:
  `relative(dirname(input), projectDir) || "."`, forward slashes.
- Pre-existing strands: bd-ip1lrgra already asks for `quarto.project`
  (notes that Q1's type stub says `profiles`, plural, but the runtime
  field is `profile`, singular — implement the singular); bd-5qepzwst
  already asks for a real `quarto.version`.

## Design

### Shared plumbing: a per-document host context in `LuaOptions`

Add one struct to `pampa::lua_options`, filled by the host, read by the
registrars:

```rust
/// What the host knows about the document and project a Lua script runs
/// for. Everything Quarto 1 surfaced through `quarto.project` and
/// `quarto.doc.{input,output}_file`. All optional: pampa's own tests and
/// the conformance suite run without a host.
#[derive(Clone, Debug, Default)]
pub struct HostContext {
    /// Absolute path of the input being rendered → `quarto.doc.input_file`.
    pub input_file: Option<PathBuf>,
    /// Absolute path of the output → `quarto.doc.output_file`.
    pub output_file: Option<PathBuf>,
    /// `None` for single-file renders (Q1: `quarto.project.directory` is nil
    /// outside a project).
    pub project: Option<HostProject>,
    /// Active profile names → `quarto.project.profile` (a `pandoc.List`).
    pub profiles: Vec<String>,
    /// The environment `os.getenv` answers from: a snapshot the host took
    /// on its own thread before any script ran (real environment, then
    /// file-defined `_environment` values for keys the real one lacks,
    /// then `QUARTO_PROFILE` forced to the active list). `None` means
    /// "no host": `os.getenv` falls through to the stdlib on native and
    /// to `runtime.env_get` on WASM, which is today's behavior.
    pub env: Option<Arc<HashMap<String, String>>>,
}

#[derive(Clone, Debug)]
pub struct HostProject {
    pub directory: PathBuf,          // absolute
    pub output_directory: PathBuf,   // absolute (== directory when no output-dir)
    pub offset: String,              // "." or "../.." — forward slashes
}
```

`LuaOptions` gains `pub host: HostContext`. quarto-core's
`lmd::lua_options(project, runtime)` keeps its signature for the
`lmd_execute` caller and gains a sibling
`lua_options_for_document(project, runtime, document: &DocumentInfo,
output: PathBuf)` used by `UserFiltersStage` and
`ShortcodeResolveTransform`. `offset` is computed once there with
`pathdiff::diff_paths(&project.dir, input.parent())` →
`quarto_util::to_forward_slashes`, `"."` when empty — exactly Q1's
`projectOffset`. `output_file` is `ctx.output_path()` (project renders set
`DocumentInfo.output` in `pass2_renderer`, so this is the final path).

Why `LuaOptions` and not new parameters: `create_filter_environment_with`
and `LuaShortcodeEngine::new_with` already take `&LuaOptions`, every
caller already builds one, and the conformance suite calls the production
constructor directly, so the fields are visible there with no synthetic
registration. Hub-client (WASM) gets the same behavior for free through
`UserFiltersStage`.

### #939 — `quarto.project` and `QUARTO_PROFILE`

New `register_quarto_project(lua, &host)` in `quarto_api.rs`, called from
both environments after `register_quarto_api`:

```lua
quarto.project = {
  directory        = <abs path> | nil,
  offset           = "." | "../.." | nil,
  output_directory = <abs path> | nil,
  profile          = pandoc.List{ "drafts", ... },   -- always a List, possibly empty
}
```

`os.getenv`: install a Rust replacement on the stdlib `os` table (native)
and on the synthetic one (WASM, `os_wasm.rs`), from one shared helper.
When the host supplied `env`, the function is a pure `HashMap` lookup
and never touches libc. The snapshot is built by the host, in
`StageContext::new` right after `load_project_environment` (the one
place that already has the real environment, the file layers, and the
active profiles together), and stored on `StageContext` as
`env_snapshot: Arc<HashMap<String, String>>` so cloning it into each
`LuaOptions` is free:

1. start from the real environment (`std::env::vars_os()`, non-UTF-8
   entries dropped; on WASM `runtime.env_get` has nothing, so this layer
   is empty);
2. add each file-defined `_environment` pair whose key the real
   environment lacks — the same filter `env_for_subprocess` applies, so
   the "real environment wins" rule of `project/environment.rs` holds;
3. set `QUARTO_PROFILE` to `quarto_profile_env_value(&active)` when the
   active list is non-empty — the documented deliberate exception where
   quarto's own variable beats the inherited one, matching Q1, which
   wrote the active list back into the environment.

Two reasons for a snapshot rather than a lookup at call time. First,
filters run under `tokio::task::block_in_place` on a worker thread, and
the stdlib `os.getenv` is libc `getenv`, which races with any `setenv`
elsewhere in the process (glibc documents this as undefined behavior,
and Rust's `std::env` lock does not cover C code). q2 never mutates its
environment in production, but engines spawn children and link
third-party code, so reading on the orchestrator thread before the
pipeline fans out is the defensive choice (Carlos, 2026-10-27). Second,
every filter and shortcode in a render then sees one consistent
environment. Layer 2 is a small step past the issue: Quarto 1 loaded
`_environment` into the Deno process environment, so pandoc's Lua saw
those variables too; without it a ported filter that reads a file-defined
variable would silently get nil. (Agreed 2026-10-27.)

The `env` shortcode handler (`EnvShortcodeHandler`) performs the same
three-layer merge at lookup time; switching it to the snapshot is a
one-line follow-up, not part of this plan.

### #940 — `quarto.doc.input_file` / `quarto.doc.output_file`

`register_quarto_doc(lua)` gains the `&HostContext` and sets two plain
string fields (absolute paths, as in Q1). Also set them on the shortcode
environment's `quarto.doc` — Q1 shortcode handlers see them, and the
Connect filter's "skip some pages by path" logic is the kind of thing that
moves into a shortcode.

Also in scope (agreed 2026-10-27): a minimal `PANDOC_STATE` global in
both environments, built from the same `HostContext`:

```lua
PANDOC_STATE = {
  input_files = pandoc.List{ <quarto.doc.input_file> },  -- empty List without a host
  output_file = <quarto.doc.output_file> | nil,
}
```

Pandoc's `output_file` is the writer's output *name* as given on the
command line; Q1 joined it with the output directory anyway
(`init.lua:669`), so the absolute path is what every Q1 filter ended up
with. The other pandoc fields (`resource_path`, `source_url`,
`user_data_dir`, `request_headers`, `verbosity`, `log`, `trace`) stay nil;
a filter that needs one gets a clear "attempt to index a nil value" at
its own line rather than a plausible-looking wrong default. Not a
registry divergence (`divergences.md`): it is a gap, not a decision
against.

Optional, cheap once the plumbing exists: `quarto.doc.project_output_file()`
(Q1 `init.lua:1090`, the project-relative output path). Include only if a
Connect filter turns out to use it.

### #941 — `os.exit` fails the document

Replace `os.exit` on both `os` tables (shared helper next to the `getenv`
one) with a Rust function that raises `mlua::Error::external(LuaExit {
code })`. Code mapping follows Lua: no arg or `true` → 0, `false` → 1,
number → that number. The second `close` argument is ignored.

In `apply_lua_filter_with`, when the script load or a handler returns an
error whose chain contains `LuaExit`, map it to a new
`LuaFilterError::Exit { code, filter: PathBuf }` whose `Display` is
`Lua filter <path> called os.exit(<code>); the document was not rendered`.
Everything downstream already does the right thing: `UserFiltersStage`
turns it into a stage error, the orchestrator records "while rendering
<file>", moves on to the next document, prints the summary, and exits
non-zero because a document failed. The exit code the filter asked for is
reported in the message, not propagated as the process exit status (q2
has its own contract there, and a render with one failed page is already
non-zero).

Decisions worth stating explicitly:

- `os.exit(0)` also fails the document. In Quarto 1 it made pandoc exit
  without writing output, which Quarto 1 then reported as a failure, so
  this is parity, not a tightening.
- `pcall(os.exit, 1)` will catch the error instead of exiting. Acceptable;
  nobody does this on purpose.
- The shortcode environment gets the same override; an `os.exit` there
  becomes whatever a thrown error already becomes for a shortcode (an
  error diagnostic on the shortcode).
- q2's `error()` is **not** changed to Q1's log-only behavior; the issue
  confirms `error()` already behaves well.

Rule compliance: the WASM `os` table gains `exit` too, so
`crates/pampa/tests/wasm_lua.rs` gets a case (per `.claude/rules/wasm.md`,
`os_wasm.rs` is on the must-update list).

### #942 — `quarto.version` as a `pandoc.types.Version`

New `crates/pampa/src/lua/version.rs`: `LuaVersion(Vec<u64>)` userdata
with

- `pandoc.types.Version(spec)` constructor accepting a string (`"1.4"`,
  `"0.36.0"`), a number, a sequence table, or another Version;
- `__eq`, `__lt`, `__le` as `add_meta_function` taking `(Value, Value)`
  so either operand may be the Version (Lua calls `__le("1.4", v)` for
  `v >= "1.4"`; `add_meta_method` would only see the Version-first
  case). Comparison is lexicographic on components, shorter prefix is
  less (`1.4 < 1.4.1`), matching pandoc;
- `__tostring` → `"0.36.0"`; `__index` for integer keys (components) and
  the method `must_be_at_least(other[, msg])`; `__len`. With `__index`
  and `__len` present, Lua 5.4's `table.concat` accepts the userdata
  (`checktab` with `TAB_R|TAB_L`), so `table.concat(quarto.version, ".")`
  keeps working — this is exactly why it works on Q1's pandoc Version.
  Pin it with a test;
- `pandoc.utils.type(v)` → `"Version"` (add to `userdata_type_name` in
  `utils.rs`).

Then:

- `register_quarto_version` builds `quarto.version` from the leading
  dotted-numeric prefix of `quarto_util::cli_version()` (Q1's
  `leadingDottedNumber`: `"0.37.0-nightly.20261027"` → `0.37.0`;
  never falls back to a plain string).
- `PANDOC_VERSION` and `PANDOC_API_VERSION` in
  `create_filter_environment_with` (and the shortcode env, if set there)
  become Version objects with the same components as today.
- `pandoc.types` becomes a real table (registered from `constructors.rs`
  or `types.rs`), holding `Version` and `Version`-related helpers only.

Check `crates/pampa/tests/lua-conformance/xfail.txt` and
`differential/xfail.txt` for Version/`PANDOC_VERSION` cases: any that
start passing must be removed from the xfail lists (the ratchet reports
them otherwise).

## Risks

- `table.concat` on a userdata relies on Lua 5.4 `checktab` metamethod
  acceptance; pampa is on `lua54` (vendored). Pinned by test; if it fails,
  fall back to a table with a metatable (`__name = "Version"`) instead of
  a userdata — `pandoc.utils.type` already reads `__name` from table
  metatables.
- `os.getenv` shadowing changes what every filter sees for one variable.
  The override only fires when profiles are active, so a render without
  `--profile`/`QUARTO_PROFILE` is byte-for-byte unchanged.
- Two more `LuaOptions` fields touch three quarto-core call sites and a
  handful of tests that build `LuaOptions {..}` literally
  (`placeholder_shortcode.rs:39`); `Default` on `HostContext` keeps the
  `with_dialects` constructor and the struct-literal sites compiling with
  one added line each.
